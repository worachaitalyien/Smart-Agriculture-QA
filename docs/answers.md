1. **Concurrent requests และฐานข้อมูล**
   ESP32 และ AI ส่งข้อมูลเข้าคนละตารางและเป็น INSERT แถวใหม่ จึงไม่จำเป็นต้องแย่งเขียนแถวเดียวกัน แต่ยังมีการแข่งขันใช้ connection, CPU, I/O และล็อกภายใน เช่น auto-increment/index ได้ การอ่าน latest ของสองตารางอาจได้ข้อมูลคนละเวลา เพราะแหล่งข้อมูลส่งไม่พร้อมกัน ควรใช้ InnoDB, transaction สั้น, prepared statements, จำกัดอัตราส่ง, retry แบบ backoff เมื่อ deadlock และถ้าโหลดสูงใช้ message queue กับ worker เขียนฐานข้อมูล สำหรับภาพ snapshot ที่ต้องตรงเวลากันต้องมี timestamp/correlation ID และออกแบบ transaction หรือ snapshot consistency ให้ชัดเจน

2. **HTTP REST เทียบ MQTT**
   HTTP มี header และรูปแบบ request/response ส่วน MQTT ใช้ connection ค้างและ packet ขนาดเล็ก จึงมักประหยัด overhead สำหรับข้อความเล็กที่ส่งบ่อย และ broker ช่วยกระจายข้อมูลไปหลายผู้รับได้ทันที แต่ HTTP keep-alive ลดต้นทุนเชื่อมต่อได้เช่นกัน MQTT ไม่รับประกันว่า latency ต่ำกว่าเสมอ ขึ้นกับ TLS, ระยะเครือข่าย, broker และ QoS โดย QoS 1 อาจส่งซ้ำ ผู้รับจึงต้องจัดการ idempotency

3. **Merge conflict**
   Commit งานของตนก่อน แล้ว fetch main ล่าสุด ตรวจ diff และเข้าใจความตั้งใจของทั้งสองฝ่าย เปิดไฟล์ที่มี conflict ลบ marker และรวม logic ที่ถูกต้องร่วมกับเจ้าของอีก branch ไม่เลือกทับทั้งหมดโดยไม่อ่าน จากนั้นทดสอบ API และทดสอบ regression ก่อน commit ผลการแก้ conflict และ push branch เดิมให้เพื่อน review ใหม่ แล้วจึง merge ตาม workflow ของกลุ่ม

4. **ใช้ LDR/BH1750 ร่วมกับ Vision**
   บันทึกค่าความสว่างและเวลาให้สัมพันธ์กับ frame ใช้ lux เพื่อเปิดไฟเสริม/ปรับ exposure ภายในขอบเขตที่ทดสอบแล้ว และแจ้งเตือนเมื่อแสงอยู่นอกช่วงที่โมเดลเชื่อถือได้ เก็บภาพหลายสภาพแสงเพื่อทำ augmentation และฝึก/ประเมินโมเดลเพิ่ม ไม่ใช้ค่าความสว่างแปลงเป็นจำนวนผลไม้โดยตรง และไม่สรุปว่าใช้ threshold เดียวได้กับทุกกล้อง ต้องทดสอบ false positive/negative และความแม่นยำในแต่ละช่วงแสง
